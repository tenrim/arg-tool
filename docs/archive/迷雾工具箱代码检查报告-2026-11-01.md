# 迷雾工具箱代码检查报告

检查日期：2026 年 11 月 1 日。对象：V1.8 发布后的本地项目。

**整体判断：项目已经有明确的架构和统一组件基础，可以继续维护；但文档、代码可读性、测试运行方式和版本管理需要集中整理。现在不需要推倒重写，也不宜继续只加功能、不整理。**

## 你关心的几个问题

| 问题 | 检查结论 |
| --- | --- |
| 代码规范是否统一？ | **部分统一。** 组件、动效、数据和计算的职责有规则；但源码排版差异较大，一些复杂逻辑被压在很长的单行里。 |
| 是否有清晰的指导文件？ | **有，但不够集中，也存在矛盾。** 项目规则、UI 规则、模块边界和测试要求都已写出，不过新旧说明混在一起，容易让维护者做错选择。 |
| 是否存在大量耦合？ | **没有发现全站互相纠缠、无法拆分的情况。** 但公共样式、笔记与图稿控制器，以及页面之间的事件通知，是改动容易牵连其他地方的集中点。 |
| 每个文件的边界是否清晰？ | **模块层面较清晰，部分文件仍承担过多职责。** 计算、存储、编辑器适配已有分工；一些页面文件仍同时负责界面、保存、弹窗、导出和跨页面联动。 |

## 已经做得好的部分

- **不是每个页面各写一套界面。** 114 个文件直接使用统一 UI 入口，按钮、输入框、弹窗和动效有公共所有者。这种共享本身是合理复用。
- **主要数据与计算有独立职责。** 例如笔记存储有自己的模块，图稿引擎有适配层，出行和财务计算把公式与页面分开。
- **规则有自动检查。** 本次前端依赖检查覆盖 363 个模块、880 条明确的导入关系，未发现循环依赖或现有规则禁止的跨界调用。
- **基础检查通过。** 590 个前端、服务、开发脚本和测试源码文件通过语法检查；共享 UI 规则检查通过；62 份当前文档中的 241 个本地链接有效。

这些结果说明项目有可用的基础，但不代表每个文件都容易维护，也不代表所有功能已经逐一实测。

## 建议优先处理的问题

### 1. 当前发布版本还没有完整对应的 Git 记录

V1.8 发布清单中，有 **13 个已上线文件尚未纳入本地 Git 跟踪**，包括新增计算、图稿交换和笔记管理文件。其他已发布修改也还留在工作区。

这不表示文件丢失：本次发布保留了文件包、清单和服务器备份。但只取出目前已提交的代码，不能完整还原 V1.8；换电脑、交接或回退时会更依赖当前工作目录。

**建议：优先整理一份与线上一致、可重复取出的正式版本。** 按发布范围核对后再提交和标记版本，不把全部未提交文件不加区分地一起提交。

### 2. 有测试，但其中一部分只能在特定本机环境运行

发现 **5 个新浏览器测试固定访问本机的 16332 端口**，自身不启动测试网站。项目的自动检查流程也没有为它们启动该服务。

因此，它们在当前已打开本地服务的电脑上可以通过，换到干净的自动检查环境时却可能直接连不上。问题在于测试的运行条件不完整，并不能据此认定对应功能失效。

**建议：让测试自行启动临时网站，或统一通过明确的测试地址运行，结束后自行清理。** 这包括最近新增的笔记、图稿和搜索测试，应优先补齐。

### 3. 指导文档有内容冲突

具体例子：项目规则中仍有“搜索默认包含五类”的旧说法，而当前架构文档和 V1.8 实际行为是默认排除科普；模块边界文档仍描述旧的 Gnuplot 绘图路径，当前函数绘图已经改用 Desmos；文档中还留有图稿输出到其他工具的旧说明。

文档链接有效，只能说明“文件存在”，不能证明里面的规则仍然正确。

**建议：建立一份简短的开发总指南，明确当前规则、文件分工和阅读顺序。** 历史决定保留为历史记录，避免与当前规范并列。已有的 README、AGENTS、UI 开发规则、模块边界和测试规范可以继续使用，不必全部另起一套。

### 4. 部分核心文件太密集，职责也偏多

例如笔记页面约 3.7 万字节，却只有约 194 行；图稿页面约 2.7 万字节，只有约 108 行，其中一行超过 1,600 个字符。这些文件同时包含界面生成、保存、导入导出、弹窗和联动逻辑。

风险不只是“不好看”：复杂操作挤在一起，更难审查先后顺序，也更容易在修一个问题时漏掉另一个分支。最近补充的笔记和图稿代码也存在这个问题，功能测试通过不能代替可维护性检查。

**建议：先统一正常排版，再按职责拆分。** 优先整理笔记页面、图稿页面和管理弹窗；保留原来的存储所有者，不因为拆文件新增第二套状态或数据库。

### 5. 公共样式集中，但内部还不够清楚

共享组件样式文件同时放着普通控件、编辑器适配、笔记、设置、字符表和在线绘图样式，前后还存在针对工作台的覆盖规则。集中管理有利于统一外观，但修改时仍需追踪“后面的规则会不会覆盖前面的规则”。

这类结构容易让按钮状态问题反复出现。本次没有确认新的按钮显示故障，发现的是维护风险。

**建议：仍由 UI 模块统一负责，但在内部按通用控件、编辑器适配、布局和特殊展示整理。** 合并重复定义，不继续靠在文件末尾追加覆盖来解决问题，保持现有配色和扫描线。

### 6. 部分联动关系藏在全局事件和页面元素里

项目有 30 类页面事件，其中“页面切换”事件被 47 个文件引用。文档和源码还显示，部分工具通过页面元素标识交接内容。

这些机制并非天然错误，但仅看某个文件的导入列表，很难知道它会影响哪些页面。因此，“没有循环依赖”不能等同于“没有隐藏的牵连”。

**建议：先明确每种事件由谁发送、谁接收、何时清理。** 新联动优先使用具名接口；旧联动按实际改动逐步收口，不做没有必要的全站重写。

### 7. 工具目录和完整科普内容仍绑定较紧

功能登记模块仍直接引用完整科普内容，用于校验功能与文章的对应关系。现在关闭科普搜索，确实会把文章排除出搜索索引，但并不等于不加载科普模块。

**建议：以后把轻量目录信息与正文按需加载分开，同时保留完整性检查。** 本次未测量启动耗时，不能把这一点直接认定为卡顿原因，优先级低于前面几项。

## 建议的整理顺序

1. **先保证能交接和复现：** 整理 V1.8 版本记录，修正依赖本机服务的测试。
2. **再统一规则：** 清理矛盾文档，明确开发入口，加入统一排版约定和检查。
3. **再处理容易牵连的代码：** 从笔记、图稿、公共样式和事件接口开始，小步整理并验证。
4. **最后优化加载：** 分离目录与完整科普正文，根据实际测量决定后续优化。

当前最值得投入的是让后续修改更可靠，而不是增加更多规则文件，或为了“文件更小”机械拆分所有代码。资料表和科普正文较大，不应因此删减内容。
